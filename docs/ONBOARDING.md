# Account onboarding

New `users/{uid}` profiles created through email, Google or phone sign-in receive an explicit version-1 `onboarding` map. Every existing student profile without a completed marker is also routed to onboarding on session restoration, including imported accounts and users already signed in when the updated app loads. Their existing details are prefilled. Their first successful save atomically adds an in-progress marker anchored to the original createdAt; it preserves email, résumé paths, import metadata, applications, team memberships and the registered-member count. No bulk migration is needed. Completion is stored against the Firebase UID, not browser storage. Different unlinked authentication identities remain separate accounts.

A welcome screen with a local illustration introduces the four saved steps. Profile questions require full name and city; college/course/specialization/study stage/graduation year; skills (or an explicit beginner answer), professional direction, introduction and career goals; then collaboration preferences and at least one teammate interest. Portfolio links are not collected during onboarding. A live private student card reflects each answer. The same uppercase name normalizer is used for phone login, onboarding and profile edits. Google names are prefilled and must pass full-name validation before continuing. Other scripts/imports and legacy names are not bulk modified.

Each Continue transaction saves private core fields in `users/{uid}`, private preferences under `careerPreferences`, the next resumable step, and the limited matching name directory in `adminUsers/{uid}`. Existing identity, email, createdAt, résumé and application records are not replaced. Save and sign out permits a partial draft and resumes on the saved step at the next login. No navigation occurs if the write fails. Back preserves the local form draft until its next successful save.

Completion atomically saves profile values, a completed timestamp, private `discoveryPreferences/{uid}` details and optional `memberProfiles/{uid}` projection. Discovery defaults off each new onboarding visit. The first consent checkbox shares name and skills with signed-in members. A separate, initially unchecked consent checkbox enables `shareDetails` and publishes role, course, college, study year, city, photo, achievements, interests and collaboration preferences. Email, phone and résumé are never placed in this projection. Existing team discovery settings can be managed in Find a team. Completed onboarding cannot be reset or removed under the rules; ordinary profile editing remains available.

Verified administrators retain their existing admin route. A global route gate intercepts all unfinished student accounts, including public return destinations after sign-in. The onboarding page resumes incomplete profiles and redirects completed profiles to a safe internal destination. Session restoration and permission failures retain the existing recovery UI. After a successful completion write and a completed profile snapshot, a welcome celebration displays the saved card and an Enter my workspace action. CSS confetti runs once on that screen and is disabled for reduced-motion preferences. Returning completed users skip this celebration. Direct protected access with a missing profile initializes it idempotently through the existing profile transaction.

Deploy `firestore:rules` before releasing Hosting. New client profile creation includes the onboarding field, so old deployed rules will reject it. The JSON schema and rules are backward compatible with profiles without this optional field. No backfill, new index, production seed or deletion is required. Missing markers cannot jump straight to completed; enrollment must first save an in-progress state. Existing completed records cannot reset or remove their marker. Rules tests cover uppercase completion, state immutability, owner-only preferences and atomic consented publication.

Required new-completion fields are enforced in the client and on the in-progress-to-completed rules transition. Previously completed profiles are not retroactively invalidated by the added requirements. Local SVG illustrations do not contact third-party image services or upload student data.

## Identity validation and focused layout

Onboarding collects required first, middle and last names separately and stores uppercase `nameParts` plus the canonical full `name` in the private user document. Existing names are split to prefill known parts; no middle name is invented. Draft saves retain the individual parts, including empty unfinished values. Profile name edits keep the structured parts synchronized. Existing completed profiles remain valid. Unfinished profiles missing the new identity fields resume at the identity step.

City accepts letters (including Indian scripts), spaces, apostrophes, periods and hyphens, with no digits. A 10-digit Indian contact number starting with 6–9 is collected with a fixed +91 prefix and stored as `mobile` in the existing canonical format. Contact entry does not change authentication providers or mark the number verified. The mobile number and name parts are never included in member discovery projections.

Text fields, graduation year, skill bounds and enum selections validate before saving. Errors appear beside fields and focus moves to the first invalid control. Server rules check new completion identity consistency, city format and mobile shape; existing completion markers are preserved. The mobile/tablet layout shows only setup and the completion welcome, while the live student card appears at widths of 1100px and above. The setup route uses a compact branded header instead of the main application navigation/footer.

## Releasing and troubleshooting

Run `npm run deploy:onboarding` from the repository root to build, deploy Firestore rules to codovate-dev, then release Hosting. It stops before Hosting if the build or rules deployment fails. A Hosting-only release can leave the new nameParts client incompatible with older rules and cause a permission rejection. The screenshot's generic banner alone cannot identify the deployed rules version. Permission failures now show the support code PROFILE_ACCESS; network/timeouts have separate retry messages. Entries remain on screen after a failed save.

The setup form is centered by default. Desktop users can open and close Preview profile; mobile/tablet users see the form only. First-step writes contain only identity/contact/city plus the progress marker. Later steps add the data collected so far. Existing résumé, portfolio and unreached profile fields are not rewritten. The name directory is updated only when missing or when the full name changes.

Authentication routes finish their active sign-in operation before the global gate redirects to onboarding. Intercepting them while a sign-in promise was still running could allow its later return-destination navigation to remount onboarding and discard edits. The regression suite verifies auth-route handling, and the browser test edits education immediately after sign-in and confirms those values persist.

## Compatibility with older account records

Existing documents may retain extra legacy fields such as fullName, role or phoneNumber. Updates validate an allowlist of changed fields, so unchanged legacy fields no longer block onboarding. Those extra fields cannot be added, changed or removed by the client; new document creation remains strict. Authorization continues to use authenticated ownership and admin token claims, never a legacy profile role.

The first successful onboarding save initializes only absent required profile defaults. Existing email, registration timestamp, résumé, portfolio and legacy attributes are preserved. A missing email can initialize only to the authenticated token email (or empty for phone-only accounts). A missing createdAt can initialize only to server request time and is immutable thereafter. This repair never increments registration counts or recreates the account.

Save denials now identify the operation with safe support codes such as PROFILE_ACCESS_READ_DIRECTORY or PROFILE_ACCESS_WRITE_PROFILE. Codes contain no UID, phone, email, tokens or personal values. These aid diagnosis if an account has another legacy shape; actual production records cannot be inspected without an authenticated Firebase connection.

## Teammate card data

Step three retains its existing layout and adds a collapsed teammate-card section for an approved Google/GitHub photo URL, up to six achievements and selected passions. These extras are optional and saved privately as `teammateCard`. Existing saved discovery details prefill the form before this step can save. Completed users can edit Discovery profile settings in Find a team without repeating onboarding. Course is included in the academic card line; older discovery records without it remain valid.

Suggested profiles use a calculated score: skill overlap 30%, same domain 20%, shared passions 15%, shared seeking preferences 10%, same college 10%, same study year 5%, and same experience level 10%. Missing data earns no points. Filters support comma-separated skills (all must match), domain, experience and student search. Connection queries are restricted to their sender or recipient; the rules use explicit equality predicates so Firestore can authorize filtered list queries.
